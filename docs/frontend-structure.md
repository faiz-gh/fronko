# Frontend structure

The frontend (`frontend/`) is a Svelte 5 + SvelteKit single-page app. Its code is grouped by feature, the same way the backend's is, so everything about one feature (its API calls, types, stores and components) sits in one folder. The [frontend README](../frontend/README.md) has the full reference: routes, components, the card data model and styling.

## Layout

```
src/
├── lib/
│   ├── core/                  # app-wide plumbing, no feature logic
│   │   ├── api.ts             # apiClient, ApiError, apiUrl()
│   │   ├── session.svelte.ts  # the signed-in user
│   │   ├── nav.ts             # dashboard sidebar registry
│   │   ├── settings-tabs.ts   # Settings page tab registry
│   │   └── theme, format, image, phone, password, cooldown helpers
│   ├── components/
│   │   ├── ui/                # shadcn-svelte primitives (generated by the CLI)
│   │   └── shared/            # used by several features: sidebar, charts/, pickers, FormSection, SectionRail …
│   ├── features/
│   │   ├── auth/  cards/  leads/  files/  teams/  orgs/  branding/
│   │   ├── signatures/  analytics/  feedback/  admin/  integrations/
│   │   └── <feature>/
│   │       ├── api.ts             # typed wrappers over apiClient for this feature's endpoints
│   │       ├── types.ts           # (when the types don't fit in api.ts)
│   │       ├── store.svelte.ts    # shared reactive state, if pages share it
│   │       ├── *.ts               # pure helpers, with *.test.ts beside them
│   │       └── components/        # the feature's Svelte components
│   └── utils.ts               # cn() and shadcn type helpers (shadcn imports $lib/utils)
└── routes/                    # SvelteKit pages; thin, composing feature components
```

## Rules

- **Features own their code.** A feature's API calls, types and stores live in its folder. Other features may import them (`$lib/features/cards/card` is used widely). `core/` and `components/shared/` import from features only where the app shell needs to: the session reads `features/auth/api`, the API client signs out `features/admin/session`, the sidebar shows cards, and the two registries below list feature pages and settings. Keep it to that; feature logic doesn't belong in `core/`.
- **No barrel files.** Import the file you need (`$lib/features/files/api`), not an `index.ts`.
- **API calls go through the feature's `api.ts`**, which uses `apiClient` from `core/api.ts`. Components don't call `fetch`.
- **Routes stay thin.** A page loads data, holds page state and lays out components. Long forms are split into sections (the card editor's are in `features/cards/editor/*-section.svelte`, listed in `sections.ts`).
- **Stores are classes with `$state` fields** in `*.svelte.ts` files, exported as one instance (`cards`, `teams`, `integrations`). Use them when several pages or the sidebar need the same data.
- **Shared components** move to `components/shared/` only once a second feature needs them.
- **Imports use `$lib`.** A `#lib` subpath import exists in `package.json` for a later migration; don't mix the two yet.

## Registries

Two lists let a feature add to the app shell without editing the shell:

- **`core/nav.ts`: `DASHBOARD_NAV`.** Each entry is `{ href, label, icon, visible?, active?, count? }`. `visible` and `count` are functions, read reactively, so an entry can depend on the session or a store. A new page adds one entry here.
- **`core/settings-tabs.ts`: `SETTINGS_TABS`.** Each entry is `{ value, label, component, visible? }`. The Settings page renders a tab per entry and keeps the open one in `?tab=`. A feature with settings adds a component and one entry.

## The integrations feature

`features/integrations/` renders whatever the backend's catalog describes, so new providers need no frontend work:

| File | Purpose |
| ---- | ------- |
| `types.ts` | `Manifest`, `Field`, `Connection`, `Activity` and friends, mirroring the API |
| `api.ts` | Catalog, connections, test, activity, OAuth start URL, SCIM tokens, email domains |
| `store.svelte.ts` | `integrations`: the catalog with each provider's connections, loaded once per user |
| `fields.ts` | Turning manifest fields into form values and back, client-side checks (`fieldProblems`), secret generation |
| `registry.ts` | Logos (`LOGOS`, simple-icons glyphs or Lucide icons), category icons, scope help text, status labels, catalog badges, search |
| `components/` | `ProviderCard` (catalog tile), `NewConnection` and `ConnectionForm` (the form built from the manifest's fields), `ConnectionPanel` (settings, test, activity, endpoints), `TokenPanel` (SCIM tokens), `DomainsPanel` (email domains), `ActivityLog`, `SecretField`, `CopyField`, `StatusBadge` |

To give a new provider a logo, add an entry to `LOGOS` in `registry.ts`. Without one it shows its initials on a neutral tile. See [Writing an integration provider](integrations/writing-a-provider.md).

## Tests and checks

```bash
npm run lint    # Prettier check + ESLint
npm run check   # svelte-check (types)
npm test        # Vitest: src/**/*.test.ts
npm run build
```

Vitest covers the plain TypeScript modules: card normalising and blocks, booking links, the signature renderer, phone helpers, and the integrations fields and registry. Components are type-checked by `svelte-check`; put logic you want to unit test in a `.ts` file next to the component.
